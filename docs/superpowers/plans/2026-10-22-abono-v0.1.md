# Abono v0.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship rastrillo's CSRF exemption for machine POSTs, then abono v0.1: Stripe memberships on a site's own key, with holdings, comps, adoption, webhooks, reconcile, partials, generated starter pages, a sandbox and an example app.

**Architecture:** Task 1 lands in rastrillo core. Everything after it is a new module, `amadan.net/rastrillo/abono`, built the way aviso and idear are. One package (`abono`) holds the service. Two internal packages sit under it: `internal/stripeapi` (the hand-rolled client and signature check) and `internal/fakestripe` (an in-process Stripe double). The double is used by the public `abonotest` package for apps' tests and by the sandbox for development. `cmd/abono` generates starter pages, and `example/` is a working app built from them.

**Tech Stack:** Go 1.25 (gate on Go 1.26.10), rastrillo (`db`, `migrate`, `csrf`, `carlos`, `sessions`, `ui`, `money`, `harness`), gorm through rastrillo's `db`, modernc SQLite, net/http (chi only in the generated pages, as rastrillo apps already use it), html/template, chromedp through rastrillo's harness.

**Spec:** `docs/superpowers/specs/2026-10-21-abono-design.md` (this branch). This plan covers the spec's slices 1 and 2. Slices 3 (one-off kinds), 4 (Connect) and 5 (migration paths for comercio and eleven) get their own plans. Patrix switching to abono is a separate plan in the Patrix repo, written after Farshad's branch `claude/dazzling-chandrasekhar-6f277c` merges.

## Global Constraints

- Module path `amadan.net/rastrillo/abono`; repository `amadan.net/rastrillo/abono`; licence MPL-2.0 (rastrillo's `LICENSE`, copied).
- `go 1.25.0` in go.mod. The gate runs on Go 1.26.10.
- No stripe-go and no Stripe SDK. Stripe API version pinned to `2025-03-31.basil`, sent as `Stripe-Version` on every call.
- Webhook signature: HMAC-SHA256 over `t + "." + body`, any matching `v1`, tolerance 5 minutes either way, several secrets accepted. Body cap 1 MiB.
- Webhook responses: bad signature or unparseable body 400; failures worth retrying 500; anything else 200.
- Migrations embedded, namespace `abono`, tables prefixed `abono_`. Timestamp columns declared `DATETIME` (modernc only decodes declared DATE/DATETIME/TIMESTAMP into `time.Time`; see idear's `schema_test.go`).
- The app merges `abono.Schema` into `BootSchema`, never `Schema`.
- Subjects are strings, the `sessions` subject. Abono never reads the app's user table.
- `past_due` grants until 30 days after `current_period_end`, never longer.
- Only subscriptions on a price belonging to an offer (sold or legacy) grant anything.
- The sandbox runs only when `Config.Origin`'s host is loopback (`localhost`, `*.localhost`, `127.0.0.1`, `::1`) and no Stripe key is set.
- Every user-facing string goes through the copy-review skill before it is written into any file. No em dashes in copy.
- Machine POST paths are exempted with Task 1's `csrf.Exempt`; each checks its own credential (Stripe's signature, `carlos.Tick`).
- Git in this environment runs with the sandbox off. Commit with `amadan commit` from a worktree whose identity is `claude` / `claude~paul@keymail.dev` (`git config --worktree`).
- Creating the `rastrillo/abono` repository and tagging any release are Paul's go-ahead, asked for at the step that needs it.

## Review Focus

1. **Finish and the webhook race for one Checkout.** The reader returns to `/subscribe/done` while `checkout.session.completed` is arriving. Expected: one subscription row, one person made (`Holder` called once), and `OnChange` may run twice harmlessly. Test in Task 5.
2. **A plan switch in the Customer Portal** (monthly to annual). Expected: the same subscription row moves to the new price's plan and keeps granting. If the new price belongs to no offer, the row becomes unrecognised, stops granting, and shows on the owner's screen. Test in Task 5.
3. **A signed-in reader paying with another address.** Expected: the holding goes to the signed-in subject (the hint), not to whoever owns that address. Test in Task 5.
4. **An event whose subscription Stripe no longer has** (404 on re-fetch: deleted in test mode, or another account). Expected: 200, logged, event recorded, no endless retries. Test in Task 6.
5. **Time boundaries.** At exactly `current_period_end + 30 days`, `past_due` stops granting. At exactly a comp's `ends_at`, the comp stops granting. Test in Task 4.

**Rules this task pins** (from spec §4.1 and Farshad's code):
- `sync` finds the row by subscription id. The plan is the plan whose prices include the subscription's first item's price, or `''`.
- A new row is created only if the subscription grants and there is a hint, or the event allows creation (the webhook passes that through the hint; see Task 6).
- The holder is resolved in this order: the hint's subject, then `abono_customers` by customer id, then `Holder(email)` for the customer's address and then the hint's. A subject from `Holder` is recorded in `abono_customers`. When `Holder` returns `""` (the app wants sign-in before payment), the row is recorded unclaimed, with `subject=''` and the address in `email`.
- `Holder` is never called for an unrecognised price.
- `OnChange(subject)` runs in the transaction for the old and the new subject whenever a row's subject, plan, status, period end or cancel flag changes.
- `Checkout` sets `mode=subscription`, the sold price for `(Plan, Interval)` (or the plan's only sold price when `Interval` is empty), and `subscription_data[metadata][abono_plan]`. With a subject it also sets `client_reference_id` and `subscription_data[metadata][abono_subject]`, plus either the subject's known customer or `customer_email`. It applies a promotion code or sets `allow_promotion_codes=true`.

### Task 6: Webhook and reconcile handlers

**Files:**

**Interfaces:**
- Consumes: Tasks 3 to 5; rastrillo `carlos.Tick`.
- Produces:
  - `const WebhookPath = "/abono/webhook"`, `SyncPath = "/jobs/abono-sync"`. These are defaults; an app may mount the handlers elsewhere and pass its own paths to `csrf.Exempt`.
  - `(*Service) ServeWebhook(http.ResponseWriter, *http.Request)`
  - `(*Service) ServeSync(http.ResponseWriter, *http.Request)`
  - `type Report struct { Subscriptions, Subjects int }`

**Rules:**
- Events read in v0.1: `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `customer.subscription.{created,updated,deleted,paused,resumed}`, `invoice.paid`, `invoice.payment_failed`, `invoice.payment_succeeded`. The id extraction is Farshad's `subscriptionID`, including `parent.subscription_details`.
- Only `checkout.session.completed` and `customer.subscription.created` may create a row. Their hint is the session's `client_reference_id` (subject) and `customer_details.email`, or the subscription's `metadata.abono_subject`.
- A re-fetch that is `stripeapi.NotFound` is logged, the event is recorded, and the answer is 200 (Review Focus 4).
- A 401 from Stripe logs that the key was refused and answers 500.
- The event is recorded after the work, with `ON CONFLICT DO NOTHING`.
- `ServeSync` is guarded by `carlos.Tick` (403 otherwise). It runs `Reconcile` inside the request and answers 204, or 500 on error.
- `Reconcile` lists every subscription and syncs each with no hint. It refreshes every price's amount, currency and interval with `GetPrice`. It then calls `OnChange` for every subject holding any subscription row or comp, each in its own transaction. `OnChange` must therefore be idempotent, and SKILL.md says so. This is a deliberate superset of the spec's "every subject whose answer moved".
