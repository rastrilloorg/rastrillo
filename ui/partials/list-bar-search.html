An ordinary form method="get", so it works with JavaScript disabled. The form sits inside a element — the HTML landmark for exactly this, baseline since 2023 — so the search region is a real element rather than a role bolted onto a form. role="search" is deliberately NOT also on the form: already carries that role implicitly, and both would announce two nested search landmarks for one search box. On an engine too old to know the element the cost is real but small, and worth stating exactly. An unknown element is display: inline, so `.rst-list > search`'s margin has nothing to apply to and the search box sits flush in a list card; the flex rule in `.rst-lbar` no-ops the same way. And the landmark is simply absent — not moved, not wrong — so the search box is still a labelled input in a working form. Both engines that old are below the floors this library already documents for light-dark() and :has(), so nothing here is the first thing to break on one. tokens.css keeps the `.rst-lbar > .rst-search` and `.rst-list > .rst-search` selectors beside the new ones, so a hand-written bare form in your own toolbar strip lays out exactly as it did. This renders the and the form it wraps, with no other wrapper: drop it straight into a
card for a list that only searches, or let list-bar wrap it in a toolbar strip. Keys: Action string, optional — the form's GET target Query string, optional — the current q value, echoed back so a search survives paging Placeholder string, optional — the field's placeholder AND its accessible name. Defaults, for the accessible name only, to T "rastrillo.ui.search_submit" ("Search" in the framework base catalog) — reusing that key rather than declaring a separate one, since its English value is exactly the string this input needs too; an app passing Placeholder always wins over T. An input with no name at all would fail WCAG 2.2 AA, so this one always has one. Hidden [][2]string, optional — extra name/value pairs to carry across the search (an existing sort order, a page size) ClearHref string, optional — where the clear ✕ goes. See below; the computed default is usually right, and page numbers are the case where it is not. Label string, optional — passed through to list-search-submit as its screen-reader text CLEARING THE SEARCH. When Query is non-empty the form also renders a ✕ beside the field, and it is a link, not script: the same Action carrying every Hidden pair, with q dropped. A real navigation, so it works with JavaScript off, it is bookmarkable, and Back behaves. The browser's own ✕ inside is suppressed in tokens.css, deliberately. It is ::-webkit-search-cancel-button and it does exactly what it is specified to do — it clears the input's VALUE. A GET form submits on submit, so nothing else happens: the results stand and the address bar still says ?q=. Leaving it beside a link that really does clear the search would be two affordances, one of which lies. Filters and sort survive a clear. They ride in Hidden, and "clear the search" is not "reset the screen". A Hidden pair named q does NOT survive: an app that carries its whole query string across the GET hands q back that way, and carrying it would give the reader a ✕ that puts the search back. PAGINATION IS THE ONE THE FRAMEWORK CANNOT DECIDE, and every app meets it eventually. Hidden is opaque name/value pairs — nothing in it says which pair is the page — so the default carries all of them, page number included, and a page number from a searched result set is usually meaningless once the search is gone. Pass ClearHref to say "and go back to page 1". */}} {{define "list-bar-search"}}
